# SplitSmart Architecture, Design, and Deployment Analysis — Codex

## Mission

Act as an independent software architect and technical analyst. Investigate the SplitSmart repository and produce a complete architecture, design, and deployment analysis. This is a documentation-only assignment. Do not implement application features, change application source code, or commit repository changes.

This analysis will be compared with a separate Spec Kit-generated proposal. Perform your own investigation and reasoning. Do not read, reference, or reuse documents generated by the Spec Kit analysis.

## 1. Repository Investigation

Inspect repository structure and current project state. Read:
- `UserRequirement.md`
- `specs/001-expense-sharing/spec.md`
- `.specify/memory/constitution.md`

Inspect other existing documentation, configuration, build files, and source code when present. Record what actually exists, what is implemented/partial/absent, mandated technology choices, customer requirements versus implementation decisions, and unresolved design choices.

Do not assume a file, class, database, service, API, or deployment environment exists merely because it would be useful. Do not edit authoritative requirements, feature specification, or constitution.

## 2. Mandatory Architecture Distinction

Analyze two scopes independently.

### A. Current Java Swing MVP
The implementation decision specifies Java 21, Maven, Java Swing, JUnit 5, and PlantUML diagram source. Analyze a suitable desktop architecture with clear presentation, domain/business logic, and persistence boundaries. The GUI delegates business rules to GUI-independent services. Monetary calculations use `BigDecimal` with explicit rounding behavior.

Distinguish existing implementation from proposed architecture.

### B. Complete Customer Product
The customer requires a primarily web-based product, Android app, and iOS app with shared user accounts and authorized data, groups, expenses, approvals, balances, payments, notifications, and reporting.

Analyze a plausible architecture supporting these platforms. Explain shared services, client responsibilities, data synchronization, authentication, authorization, and deployment boundaries.

Do not represent the Swing MVP as satisfying web/mobile requirements. Explicitly describe the gap and architectural evolution required.

## 3. Required Deliverables

Create an independent package under `docs/architecture-analysis/codex/`. Use the same document names and diagram filenames as the Spec Kit package for direct comparison.

### README.md
Describe purpose, scope, package contents, diagram rendering instructions, assumptions, and the distinction between desktop MVP and complete product.

### architecture-analysis.md
Include:
- Executive summary and architectural goals.
- System context, boundaries, stakeholders, and external dependencies.
- Functional and non-functional architectural drivers.
- Proposed logical architecture and architectural layers.
- Component responsibilities, interfaces, and dependencies.
- Key architectural decisions, rationale, alternatives, and trade-offs.
- Authentication, authorization, privacy, and security.
- Error handling, audit logging, and observability.
- Reliability, performance, scalability, maintainability, and testability.
- Architectural risks and unresolved decisions.

### design-analysis.md
Include:
- Domain concepts, entities, and relationships.
- Responsibilities of users, groups, memberships, expenses, shares, approvals, balances, payments, notifications, and reports.
- Proposed classes, interfaces, services, and boundaries.
- Expense submission and approval workflows.
- Equal and percentage-based splitting.
- Monetary precision, rounding, and remainder allocation.
- Balance calculation and payment settlement.
- Validation, authorization, transaction, persistence, and consistency considerations.
- Error and exception behavior.
- Testing strategy, edge cases, and representative scenarios.

The specification requires positive expense amounts, percentage totals of exactly 100%, and remainder allocation by largest fractional share, with participant selection order as the tie-breaker. Preserve these rules. The payer is recorded separately from participants and may or may not be a participant. Balance calculations must account for this distinction.

Do not invent implementation details or present proposed classes as existing code.

### deployment-analysis.md
Analyze deployment separately for the desktop MVP and complete customer product. Cover:
- Runtime environments and deployment topology.
- Desktop packaging and distribution.
- Web hosting and client/server boundaries.
- Android/iOS distribution.
- Application services, data storage, and receipt-image storage.
- Identity and access management.
- Notification delivery.
- Network boundaries and security controls.
- Configuration and environment separation.
- Build/release pipelines, versioning, and updates.
- Backup, recovery, monitoring, and operations.
- Deployment risks and infrastructure decisions requiring approval.

Distinguish recommended infrastructure from infrastructure verified in the repository.

### requirements-traceability.md
Map customer requirements and specification IDs to architecture decisions, design elements, components/services, relevant diagrams, and verification/test approaches. Identify requirements not met by the Swing MVP. Do not claim a requirement is fulfilled merely because a proposed architecture could support it.

## 5. Analysis Standards

For important statements and recommendations, distinguish:
- **Verified** — directly supported by repository files or implementation.
- **Required** — mandated by customer requirement or constitution.
- **Proposed** — recommendation not yet approved or implemented.
- **Assumption** — temporarily used because information is missing.
- **Open decision** — requires stakeholder/developer input.

Reference repository paths and requirement IDs wherever practical.

Do not fabricate implemented functionality, source files/classes/interfaces, database tables/schemas, API routes/contracts, infrastructure/cloud services, test results/performance measurements, or security certifications/compliance status.

When information is missing, explain what is unknown, why it matters, and what decision is needed. Evaluate technology choices against project constraints, requirements, maintainability, complexity, cost, and platform coverage rather than popularity alone.
